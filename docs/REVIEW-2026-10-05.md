### What the checked-in code does (and does not) establish

- The Twelve Data callback `on_event()` calls `check_position(price)` on every
  accepted price event. Its broad exception handler silently drops exceptions,
  so the CSV alone does not explain why a Twelve Data run failed to close.
- The `DATA_SOURCE=MT5` forward-test loop `run_mt5_test()` evaluates each closed
  candle but does **not** call `check_position()` or otherwise inspect the bar's
  high/low against the active trade. `evaluate_candle()` does not manage exits.
  If the deployed service uses MT5 feed mode, this is a direct code-path defect
  that can leave a paper trade active indefinitely.
- `TRADING_MODE` is `FORWARD_TEST` in the checked-in engine, but that does not
  prove which revision/configuration is running on the host. The checkout has
  no `.env`, no `xm_data/` output, and no production logs; the deployed
  `DATA_SOURCE` and process health remain unverified.
- `check_data.py` passes because the CSVs are structurally consistent and
  `status.json` agrees with the ledger count. It does not validate whether an
  open trade should already have crossed its SL/TP.

**Do not hand-edit `status.json` or append a guessed close to `trades.csv`.**
First confirm the deployed revision, service and `DATA_SOURCE`. Then fix/test
the appropriate exit path and reconcile #125 from the ordered price/tick
history. If the host is using Twelve Data, inspect the engine journal around
2026-10-01 07:10–07:25 UTC and the suppressed callback errors; if it is using
MT5, add candle-range exit handling with a conservative stop-first tie-break
and a regression scenario. Keep `TRADING_MODE=FORWARD_TEST`; the separate LIVE
order path is not ready.
